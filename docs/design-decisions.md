# Design decisions

This file preserves product choices and their reasons. Evaluation-only decisions are
excluded from the public edition; retained IDs stay stable for reference. Current local
coverage and historical evidence limits are described in [validation](validation.md).

## Decisions

| ID | Decision | Choice | Reason |
|---|---|---|---|
| D-01 | Runtime | Node.js, standard library only; `engines` `>=22`; verified on 26.8.1 | Present on the build host, needs no install, and one language serves tools, server and view. |
| D-02 | Dependency policy | Zero runtime and development dependencies; no package installs | Installs are approval-gated, the view must make no external requests, and less machinery is the design principle. |
| D-03 | Unit test framework | `node:test` with `node:assert/strict`, run by `npm test` | Built into the runtime, so tests need nothing installed. |
| D-04 | Browser test runtime | Python Playwright 1.59 with headless Chromium, run by Framework Python 3.12 (`/Library/Frameworks/Python.framework/Versions/3.12/bin/python3.12`) by default; `WATCHOVER_PYTHON` overrides it, and plain `python3` is used only when that interpreter is absent | Verified at preflight and rechecked in C0; the build host's default `python3` lacks Playwright, so the working default names the interpreter that has it. |
| D-05 | Module format | ES modules (`"type": "module"`) | The same freshness module can load in Node tests and in the browser without a bundler. |
| D-06 | File layout | See "Repository layout" below | Mirrors the build targets named in the design freeze, one group per concern. |
| D-07 | Test layout | `tests/**/*.test.mjs` for Node suites, `tests/browser/` for Playwright, `tests/helpers/` for test-only utilities | Keeps test-only code out of product modules. |
| D-08 | License holder | MIT, "WatchOver AI DevOps contributors" | MIT needs a holder; a collective name avoids personal identifiers. |
| D-09 | Package version | `0.1.2`, with the existing state/event schema unchanged | Public packaging and wording adapt the accepted patch version without adding features or migrating records. |
| D-10 | Ignored paths | `node_modules/`, any `evidence/` directory, Python caches, OS files | Evidence never enters git (FT-3); the rest is build-host noise. |
| D-11 | Schema format | JSON Schema 2020-12 files `schema/state.schema.json` and `schema/event.schema.json`, identified by URNs | A standard, readable format a fresh AI can follow; URNs avoid any real domain. |
| D-12 | Supported JSON Schema keywords | `$schema`, `$id`, `$comment`, `title`, `description`, `$defs`, `$ref`, `type`, `enum`, `const`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `pattern`, `format`, `minimum`, `maximum` | Small enough to implement and review in full; any other keyword makes the schema fail to load. |
| D-13 | Validator limits | In-repo validator; `$ref` only to local definitions, `$defs` only at the root, `format` only date-time, `enum` and `const` only JSON primitives, `additionalProperties` only true or false | Needs no install and keeps behaviour predictable; anything outside these limits fails closed with keyword and JSON pointer. |
| D-14 | Naming | snake_case properties; fact statuses are the exact FT-7 strings; every other enum is lowercase snake_case | FT-7 fixes the status strings; one simple convention for everything else. |
| D-15 | Stage values | recon, plan, awaiting_decision, executing, verifying, handoff, incident, recovered, teardown, closed | One value per Annex E stage; "provisioning or executing" maps to executing and "handoff or running" to handoff. |
| D-16 | Fact classes and freshness caps (minutes) | identity 1440, permission 240, resource 240, health 60, source 1440, price 43200, network 240, other 1440 | Every fact states its own freshness rule, which may be shorter but never longer than its class cap, so freshness cannot be extended indefinitely (Annex D.5). |
| D-17 | Trust versus outcome | A fact may carry `problem: true` only when it is a verified or stale (previously verified) observation that shows something wrong | A verified failure is trustworthy knowledge but must never read as healthy; an unverified assertion cannot flag one. |
| D-18 | Linking to facts | Resources, source local changes and the deployed ref point to facts by key | One freshness and evidence mechanism for everything that can be checked. |
| D-19 | Secret patterns and canary | Fifteen finite credential patterns, each with an obviously fake canary checked on every validation; findings report pattern, file and line only | A clean scan is trusted only when every pattern has just proven it still fires, and output never repeats a secret. |
| D-20 | Validation order | Scanner self-test, schema load, secret scan (always runs), JSON parse, schema validation, then named checks only if the shape is valid | Fails closed at every step, never skips the secret scan, and avoids cascades of follow-on errors. |
| D-21 | Mode values | Only basic | Guarded mode's interface is deferred; adding the value later is a schema change. |
| D-22 | State bounds | Every list has maxItems, every string a length bound, every number a range, and every object a closed property list; a static test enforces this | State stays bounded and is overwritten in place; history lives in events. |
| D-23 | Fixture layout | `fixtures/valid/lifecycle/NN-step/`, `fixtures/valid/status/<status>/`, `fixtures/valid/scenarios/<name>/` (provider-neutral examples of the view handoff, services, names, shared objects, interruptions and a package gap), `fixtures/packages/<name>/package-omissions.json` (a declared reduced skill package), `fixtures/invalid/<case>/` with `expected.json` | Each fixture is a real workspace the view can serve later; `expected.json` proves an invalid fixture fails for its intended reason. |
| D-24 | Validate interface | Module functions `validateWorkspace` and `validateTexts`; the command name is chosen in C2 with the other commands | Command names are a C2 default; appending needs to validate text before it is written. |
| D-25 | Event types | stage_change, intent, result, decision_request, decision, fact_verified, plan_failure | One type per Annex F required event; there is no free-form note type. |
| D-26 | Evidence locators | `evidence/<relative path>` with no parent-directory segments | Locators stay inside the workspace's evidence folder, which the view never serves. |
| D-27 | Evidence scanning | Every regular file under `evidence/` is secret-scanned on each validation, even when state or events are missing or malformed; symbolic links and special files are reported and never followed; files over 16 MiB are reported and not scanned | No readable evidence escapes the scan, nothing outside the workspace is read, and an unscanned file never passes silently. |
| D-28 | Output redaction | Every string in validation output passes through the secret patterns; JSON pointers are redacted segment by segment after unescaping | Output must never repeat secret-shaped input, including property names, identifiers and file names. |
| D-29 | Approval lifecycle | Request ids are unique; each request gets at most one decision; every unanswered request is the pending decision, matching its id, categories and request time; a gated intent relates to an earlier approved decision | The Annex G authority path can be replayed from events, and only an approval authorizes a gated action. |
| D-30 | Fact provenance | A current VERIFIED or STALE fact matches the latest promotion event for its key in status, check time and evidence; ASSUMED facts come from reasoning | The current state cannot claim more, or different, verification than the history records. |
| D-31 | Record size limits | Timestamps at most 35 characters, event ids at most 16, state.json at most 2 MiB, each events line at most 16 KiB | Closes the length gaps that patterns and number ranges cannot, such as a very long fraction or number. |
| D-32 | Unanswered requests | A request cannot be withdrawn silently; the human's reply, even "deferred" or "changed", is recorded as its decision | Keeps every request traceable to an answer without a separate withdrawal mechanism. |
| D-33 | Commands and exit codes | `node tools/watchover.mjs init`, `append`, `validate` (C3 adds `show`); exit 0 done, 1 refused or invalid, 2 appended but the workspace needs a state.json update, 64 usage error | One entry point with no install; exit codes let an AI tell a refusal from a pending state update. |
| D-34 | Workspace layout | One folder, by convention `watchover/` inside the project, holding `state.json`, `events.jsonl`, `evidence/` and `README.md`; init refuses a folder that already has content | Keeps the records together, easy to find and never mixed into existing files. |
| D-35 | Pointer file | `README.md` in the workspace names the router skill by absolute path, then state.json and recent events | A fresh AI can find where to start from a plain file; nothing depends on a client auto-loading it (FT-6). |
| D-36 | Router skill path | `skills/router.md` | The pointer file and the initial handoff name it; C4 creates it. |
| D-37 | What append fills in | `schema_version`, `id` (the next number) and `at` (the current UTC time, never earlier than the last event), only when the event omits them | Removes the error-prone parts of writing an event; everything that carries meaning still comes from the AI. |
| D-38 | Append validation scope | Before writing, the event log as it would be: secret scan, size, JSON, schema and event-only named checks; afterwards the whole workspace is validated and reported | A state update follows its event, so cross checks with state.json are reported after the append rather than blocking it. |
| D-39 | Writers | One AI writes a workspace at a time; there is no file locking | Basic mode has a single AI; locking would be machinery without a user. |
| D-40 | Serving | `show` binds 127.0.0.1 only, default port 7431 (`--port` overrides); GET and HEAD only; an exact-path allowlist of the view files, state.json and events.jsonl; the Host header must name the loopback address; a content-security policy allows only same-origin resources | Read-only and local by construction; evidence and every other file are unreachable, and matching paths as received leaves nothing for traversal to exploit. |
| D-41 | Refresh | The view re-reads state.json and events.jsonl every 5 s; an on-disk change is declared to appear within 10 s | Quick enough to follow live work, light enough for a local file read; the bound covers one interval plus fetch time. |
| D-42 | No recent update | A "No recent update" banner appears when the state is older than 15 minutes | Long enough for normal pauses between updates, short enough that a stalled AI is noticed; the page never implies progress it has not been told about. |
| D-43 | Long-operation threshold | An operation expected to take more than 3 minutes is recorded as long-running: intent first with an expected duration range, result after; the view flags one that runs past its range | Around the point where a person watching starts to wonder whether something is stuck. |
| D-44 | Rendering | A pure renderer turns state, events and the clock into escaped HTML; the page shows it, and on any read or parse failure replaces it with an error rather than keeping old content | Most view obligations are testable without a browser, recorded text can never become markup, and a broken record is never shown as if current. |
| D-45 | Look and status colours | Logbook styling with local fonts only; each status has a symbol, words and its own colour; green only for verified and fresh, with local and remote told apart by border and words; times in UTC | Status is never colour alone, and nothing but verified-and-fresh can read as green. |
| D-46 | Browser evidence | Browser checks run from `npm test`; setting `WATCHOVER_SCREENSHOT_DIR` keeps a full-page screenshot of every valid fixture | Screenshots are evidence outside git, produced by the same checks that verify the view. |
| D-47 | Skill layout and length budget | `skills/router.md` at most 170 lines; `skills/stages/<stage>.md` at most 90 lines each; full provider profiles at most 110 lines; skeleton profiles at most 40 lines | Short enough to read in full at the start of a session; the router plus one stage file and one provider stays small. |
| D-48 | Rules in every stage file | Each stage file ends with a short "Always" block restating the secrets, re-verify, logging, seven-status and gate rules from the router | A stage file read on its own still carries the rules that matter most. |
| D-49 | Provider status wording | GCP says "validation pending"; Cloudflare DNS, AWS, Azure and Nectar say UNVALIDATED | GCP is the first provider profile under validation, and even it is not yet validated; the product itself is provider-neutral and nothing claims more than it has shown. |
| D-50 | Local targets | `provider_profile` may be `local`, with no provider file; the plan uses one tier with a cost range of 0 to 0 and says so; plan acceptance is asked before the first change | A local run has no billable gate, so the plan explanation goes into the plan-acceptance request without inventing a cost. |
| D-51 | Catalog fields | `id`, `name`, `kind` (cli, mcp, api, web), `provider`, `stages`, `source` ("Publisher: official document or repository", not a web address), `install_or_access`, `permissions`, `risk` (level and note), `last_checked`, `check_status`, `check_note`, `cli_fallback`, `loaded_by_default`; 17 entries; `last_checked` null with `check_status` UNKNOWN | Covers every field the freeze asks for; no online check was made, so none is claimed and no date is invented. |
| D-52 | Neutrality scan | `node tools/neutrality-scan.mjs <denylist> [--root <folder>]`; case-insensitive substring match over regular files, skipping `.git` and `node_modules`; the denylist must live outside the scanned folder; the first term is planted in a temporary control file and must be found in the same pass; output names file, line and term number only; exit 0 clean, 1 hits, 2 control failed or usage error | Whoever holds the protected terms can run it; the builder sees only the verdict and locations, and a clean result counts only when the control fired. |
| D-53 | Documentation layout | `README.md` (definition, quick start, Validated, Development evidence and Roadmap), `SECURITY.md`, `docs/architecture.md`, `docs/design-decisions.md`, `docs/validation.md`, `docs/provenance.md` | Keeps runnable product guidance, honest evidence limits and process attribution together; excludes evaluation-only procedures and placeholders. |
| D-57 | Clock problems | A verified fact whose check time is after the viewing clock is never current or green; it shows as "verified at a future time (check the clocks)". A state updated after the viewing clock is not recent and shows a "Clock problem" banner instead of "No recent update". Any later time reads as "in the future" | Freshness is computed from the clock, so a disagreement between clocks must never look like fresh evidence or recent progress. |
| D-58 | Public domain policy | Generic `example.com` names and the frozen schema dialect remain allowed; tests allow only three exact public repository URLs for documentation and their test allowlist | HELM attribution and related public tools need precise links; no domain-wide or username-wide privacy exception is granted. |
| D-59 | Safe state submission | `commit-state <workspace> --file <candidate>`: full candidate validation including cited-evidence existence, temp file in the same folder, fsync, a final stale check of `state.json` and `events.jsonl`, rename, best-effort folder sync; exit 2 when a post-check fails after replacement | Lets an AI replace the one current state without ever leaving a half-written or unvalidated file, while hand editing keeps working; a single writer is assumed and said so. |
| D-60 | Takeover summary | `brief <workspace> [--now <time>]`: refuses an invalid record; at most 30 lines; facts needing attention first with remaining minutes from the view's own freshness code; exact omitted count pointing to `state.json /facts`; recorded approvals shown as history | A fresh session orients quickly without a second stored summary, and the CLI and the page never disagree about freshness. |
| D-61 | Service rows | One `health.<component>` fact per component, class `health` (window at most 60 min), `scope` starting with the host resource id; the view derives a Services list from these facts and resources | No new schema or upsert: service status is ordinary facts, shown as the last recorded observation, never as a live check. |
| D-62 | Provider-neutral core | Generic rules (ids versus real names, declared versus observed, shared-object deltas, interruptions, the owner after deployment) live in the router and stage files; provider files only illustrate them | The product guides any deployment target; one provider's examples must not become its rules. |

## Repository layout

```
skills/            router skill, stage skills, providers/
schema/            current-state and event schemas
app/web-ui/        read-only, self-refreshing view
tools/             capabilities: initialize, validate, append, show
fixtures/          valid and invalid synthetic state/event fixtures
tests/             Node suites; browser/ for Playwright; helpers/
integrations/      catalog.json
docs/              architecture, design decisions, validation, provenance
README.md  SECURITY.md  LICENSE
```

These eight directories contain the public product and its meaningful checks.
